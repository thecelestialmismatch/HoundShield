METHODHow this was measured, and where it can be wrong

Two passes were run: one including tests as entry points, one excluding them. The difference isolates modules that exist only to be tested — code with a test but no caller.

Every candidate below was then re-checked by grep across the whole repo, including proxy/, browser-extension/, sdk/ and docs/, because the app is not the only consumer.

Stated limits. The graph resolves static import, export … from, side-effect imports, import() and require(). FINDING 01The shipped proxy was quarantining ordinary English

F-01

Ten of ten normal sentences blocked at HIGH risk

Critical Fixed

This was not on the list the audit set out to produce. It surfaced while building a false-positive control set for the parity guard below, and it is the most consequential thing in this document.

The Task order / delivery order rule, in both registries, read:

/\b(?:task order|delivery order|TO|DO)\s*(?:no\.?|#)?\s*[A-Z0-9]{4,}/gi

Two defects, both caused by the i flag. The alternation has no closing \b, so bare TO and DO match inside ordinary words — to|morrow, to|night, do|cument, do|wnload, to|gether. And under i, [A-Z0-9]{4,} matches any word at all, so the "order number" was satisfied by production, review, Monday.

Verified end-to-end through the real scanMessages() in proxy/scanner.ts — not a transcribed regex — before and after:

PromptBeforeMatched onAfter
Going to production on ThursdayQUARANTINE"to production"ALLOW
We need to document the rollback stepsQUARANTINE"to document"ALLOW
Please download the onboarding documentQUARANTINE"download"ALLOW
Can we move the standup to 4 PM tomorrow?QUARANTINE"tomorrow"ALLOW
What is the total spend to date?QUARANTINE"to date"ALLOW
Summarize our CAGE code 1ABC2 contractBLOCKCAGE codeBLOCK

The scanner applies every pattern directly, with no context gating, and takes the strongest verdict — so a single noisy rule decides the outcome for the whole prompt. In practice any prompt containing "to " followed by a four-or-more character word was held for review.

Why it matters
This is the failure mode that ends a DLP deployment. An operator who sees "Going to production on Thursday" quarantined does not file a bug — they switch the proxy off, and every real CUI block after that never happens. It also lands on the demo script, where the prompt before the CAGE-code one is ordinary prose.
Fix
Closing \b on the alternation, and a (?=[A-Z0-9]*\d) lookahead so the identifier must contain a digit. 10/10 benign sentences now pass; 5/5 real task-order forms still fire (TO 0001, delivery order N0001923D0001, task order no. 88213). Applied to both registries, byte-identical.
Guarded by
All ten sentences are now regression anchors in the parity corpus, asserted clean against both engines. p99 scan latency unchanged at 0.684 ms against a 10 ms budget.
VERIFIED — before/after run through proxy/scanner.ts; pattern floor 34 ≥ CI minimum 33; proxy suite 92/92.

FINDING 02The two detection registries had drifted, and the guard could not see it

F-02

Mode B missed PHI the hosted demo blocked

Critical Fixed

HoundShield maintains two independent pattern registries by design: proxy/patterns/index.ts (33 patterns — the shipped Mode B product on customer infrastructure) and lib/classifier/*-patterns.ts (53 patterns — the hosted plane and the PDF evidence generator). The split is deliberate and documented, and it is guarded by lib/detection/__tests__/registry-drift.test.ts.

That guard compares declared names and categories as source text. Its own header says so, and names the consequence: "two patterns sharing a name with different regexes still pass." This audit is the first evidence that the anticipated failure has actually happened.

Of 18 rules present in both registries, 15 are byte-identical copies and 3 have diverged. The material one is Health plan beneficiary number — the PHI rule that Rachel, the lead ICP, buys the product for. Both regexes were extracted from source and run against realistic strings:

PHI stringMode B — shipped proxyHosted plane
Patient subscriber ID A9931204 needs prior authMISSBLOCK
policy number 88213345 for the claimMISSBLOCK
group number 4471209 on the cardMISSBLOCK
memberID 4471209823MISSBLOCK
insurance # 55192837MISSBLOCK
health plan id 90210XTBLOCKMISS
member id: 887711209BLOCKBLOCK
beneficiary number 100244BLOCKBLOCK

The drift is bidirectional but asymmetric against the product you ship. The hosted plane recognises subscriber, policy and group identifiers and accepts 4–20 character IDs; the proxy recognises none of those three and requires 6–15. The demo a healthcare buyer is shown blocks five strings that the deployment they install would let through.

The other two divergences are lower severity but real: Program office / DoD system identifier — the hosted plane matches PM, the proxy does not; and NIPRNet / SIPRNet references — the hosted copy has an unescaped . where the proxy escapes it, making it marginally looser.

Why it matters
Mode B is the deployment the CUI-safe and HIPAA claims rest on. A detection gap there is a product-integrity issue, not a code-tidiness one — and the audit PDF is sold as assessment evidence.
Impact
Closing it is a regex change in one file, no architecture work. Merging both registries is the larger fix and is not required to stop the bleeding.
Risk
CLAUDE.md forbids replacing proxy patterns — extend only. CI enforces ALL_PATTERNS.length >= 33. Widening the proxy regex to match the hosted one satisfies both. Widening also raises false positives on group number in non-PHI text; tune with the existing corpus before shipping.
Plan
1. Port the hosted Health plan beneficiary number regex into the proxy, and PM into the program-office rule. 2. Escape the . in the hosted NIPRNet rule. 3. Upgrade the drift guard from name comparison to behavioural comparison — assert both registries agree on a shared corpus of fixture strings. That closes the blind spot permanently and is the guard's own documented upgrade path.
VERIFIED — both regexes parsed out of source and executed; 15 identical / 3 drifted computed over 18 shared rule names. Guard limitation quoted from lib/detection/__tests__/registry-drift.test.ts lines 33–36.

FINDINGS 02–03Built, tested, and never connected

F-03

The session-start health check reported nothing

High Wired

lib/health/service-status.ts is 431 lines whose own header says it defines "what /api/health reports, and which of it means a control is actually doing its job." Nothing imports it. app/api/health/route.ts is 16 lines returning {status:"ok"} unconditionally, and app/api/admin/health/route.ts — 28 lines — does not import it either. lib/auth/reset-diagnostics.ts (85 lines, "password-reset readiness for /api/health") is orphaned the same way.

The health route was deliberately reduced to a liveness probe so it would not disclose topology — a sound decision. The diagnostics were simply never re-homed on the protected endpoint.

Why it matters
CLAUDE.md's Session Start Protocol instructs every session to curl /api/health to check integration health, and the Integration Status table claims that endpoint reports missing control stores and reset-code configuration as degraded rather than green. It cannot — it is a constant. The documented check currently returns ok whatever the state of the system.
Impact
This is a restore-or-retire decision, not a deletion. Wiring both modules into /api/admin/health recovers 516 lines of working, tested diagnostics. Deleting them removes the capability and the stale documentation together.
Risk
Deleting is the higher-risk option: it silently makes the CLAUDE.md protocol permanently false. Wiring is low-risk — the endpoint is already admin-gated and 404s unauthorised callers.
Plan
Wire both into /api/admin/health, then correct the CLAUDE.md Integration Status row to name the admin endpoint rather than /api/health. If you would rather retire them, delete both plus their tests and fix the same row.
VERIFIED — full text of both health routes read; no import of either module in the repo.
F-04

/api/chat bypassed the shared rate limiter built for it

High Fixed

Twenty-three routes call enforceRateLimit from lib/rate-limit-shared.ts, which counts in Postgres so the ceiling is shared across instances. Two routes — /api/chat and /api/gateway/ollama — instead call createRateLimiter from lib/rate-limit.ts, an in-process Map.

rate-limit-shared.ts exists precisely because of this. Its header names the exposure: "On Vercel Fluid Compute every instance has its own Map, so the real ceiling is (limit × live instances) and it resets on each cold start. For a route that bills OpenRouter per request that is a spend exposure, not a nitpick."

/api/chat is exactly that route — 521 lines that fall back to the server's own OPENROUTER_API_KEY when the caller supplies none, limited to 10/min per instance. /api/gateway/ollama proxies to localhost and carries no cloud spend, so it is materially lower severity.

Impact
Swapping one route to enforceRateLimit closes a founder-billed spend path. Roughly a ten-line change.
Risk
Low. The shared limiter fails open to the in-process limiter by design, so a Postgres blip degrades rather than 429s. Confirm migration 028_rate_limit_buckets.sql is applied in production first — until it is, the shared limiter silently falls back anyway.
Plan
Move /api/chat to enforceRateLimit with LLM_RATE_LIMITS. Leave /api/gateway/ollama as-is and add a one-line comment saying why, so the asymmetry stops looking accidental.
Do not
Delete lib/rate-limit.ts. It is not dead — the shared limiter imports it as its deliberate fallback.
VERIFIED — importer counts 23 vs 2; /api/chat LLM fallback read at lines 449–500.
